C++ 八股复习笔记

适用岗位：游戏客户端开发（校招/实习）。本文按”一问一答纠错”的方式整理，蓝色框是复习时真实产生过的疑问与解答，红色框是必须警惕的易混点。
主线记忆：“指针赋值拷的是地址，值拷贝造的是新对象；move 只贴标签，搬家靠构造。”

一、速览卡片

# 考点 一句话说明
① 虚函数表与 vptr 虚表编译期生成于 .rodata，vptr 在对象首部、构造时写入，运行时经 vptr 决议虚函数

二、逐考点详解

① 虚函数表与 vptr

动态多态的三要素：继承 + 虚函数重写 + 通过基类指针或引用调用。三者缺一，多态不成立。

  • 虚表（vtbl）：编译期由编译器为每个含虚函数的类生成，存在只读数据段（.rodata），全类只有一份，与创建几个对象无关。
  • vptr：存放在对象内存布局的最前面（64 位下占前 8 字节，在成员变量之前），每次构造对象时由构造函数里编译器插入的代码写入——不是链接期初始化，链接器根本接触不到运行时创建的对象。多继承时对象里有多个基类子对象，每个都可能有各自的 vptr，各指向各的虚表。
  • 虚函数代码：和普通成员函数一样在代码段（.text），对象里只存指向虚表的指针。

构造/析构期间的 vptr 切换（面试加分项）：构造 Derived 时先执行 Base()，此刻 vptr 指向 Base 的虚表；Base 构造完、进入 Derived() 时改写为 Derived 的虚表。析构正好镜像：Derived 析构函数体执行完后切回 Base 虚表，再执行 ~Base。

构造期间 vptr 写 2 次（Base 版 → Derived 版），析构再写 1 次切回 Base 版

推论：构造/析构函数中调用虚函数不发生多态——此刻 vptr 还指着本类的表，调用的是本类版本。

⚠️ 易混淆点：三种"赋值"的本质区别
指针赋值拷的是地址，访问的还是原对象；值拷贝造的是新对象，新对象的 vptr 由它自己的构造函数写入，与数据来源无关；new 表达式会先构造一个堆对象再返回其地址。

Base* p = &d; —— 无新对象，p 指向原对象（Derived 虚表）
Base b = d; —— 栈上新对象，切片，vptr 指向 Base 虚表
Base* p = new Derived(); —— 堆上新对象，经典多态写法，记得 delete
Q：nullptr 上调用成员函数会怎样？

A：普通成员函数若不访问成员，编译期地址已定，this 只是传进去但从未解引用——可以正常打印；一旦访问成员就要解引用 this（地址 = this + 偏移），立刻段错误。虚函数必崩：调用第一步就要读对象首部的 vptr，nullptr 连对象都没有，第一步就倒下。
记忆：普通函数是"编译器指路"，虚函数是"通过 vptr 自己找路"——没有对象就没有路标。
⚠️ 易混淆点：基类析构函数必须是 virtual
Base* p = new Derived(); delete p; —— 若 Base 析构不是虚函数，只会执行 ~Base()，Derived 部分（构造函数里申请的资源）永久泄漏，且严格来说属于未定义行为。口诀：有虚函数的类，析构必 virtual。delete 的析构顺序是从子到父，与构造镜像。

② 左值、右值与移动语义

定义：左值 = 有身份（identity）的表达式——有名字、可取地址、可持续存在；右值 = 临时的、将亡的表达式——字面量、临时对象、std::move(a)、返回值。

Q：std::move(x) 到底做了什么？之后 x 还能用吗？

A：什么都没搬。std::move(x) 等价于 static_cast<T&&>(x)，只是给表达式贴上"我是右值"的标签，零开销，x 的内存此刻毫无变化。真正搬家的是之后被选中的移动构造函数/移动赋值。move 之后 x 处于"有效但未指定"状态：不能假设它的值，但可以重新赋值接着用。
Q：参数 void f(std::string&& s) 里，s 是左值还是右值？想把 s 的资源转出去该怎么写？

A：类型是右值引用 ≠ 它是右值。有名字的右值引用是左值——右值引用只是"我准备好了被搬"的入场券，进门之后它是有名字的活人，想用就用。所以 g(s) 走拷贝；想转资源必须 g(std::move(s))，每层传递都要自己重新贴标签。
注意：g(&s) 是错误答案——传地址只是告诉对方"对象在哪"，属于借用，不转移所有权；而且类型对不上（string* 不能传给 string 按值参数）。
Q：std::string d = std::string("hi"); 调用了什么构造？

A：C++17 起这是保证的拷贝消除：临时对象直接构造在 d 的内存里，拷贝和移动都不调用，只调一次普通构造函数。C++17 之前理论上会调移动构造。类比：商家不再把货寄到中转仓再转寄，而是直接寄给买家，仓库环节整个砍掉。

输出题（构造列表 + 左值陷阱）：

Q：为什么 B(B&& o) : A(o) 里 A 部分走的是拷贝构造（b）而不是移动构造（c）？

A：初始化列表本质是一串函数调用，A(o) 就是用表达式 o 去调用 A 的构造函数做重载决议。o 有名字、是左值表达式 → A(A&&) 绑不上左值直接出局 → 只剩 A(const A&) 能接（B 隐式转 A），于是拷贝构造胜出。想走移动必须显式写 A(std::move(o))，输出才是 c3。
语言为什么这样设计：若右值引用参数自动是右值，移动构造里连用一下参数都做不到。安全且显式。
拷贝消除之外的补充
对 int、指针这类没有资源可抢的类型，move 退化成一个拷贝——标签贴了，但移动构造本质上就是拷贝内容。是否展开、是否消除，均由编译器按优化等级自行判断。

③ new/delete、malloc/free 与野指针

核心对比：

new / delete malloc / free
身份 C++ 运算符（可重载） C 标准库函数
返回值 带类型的指针 void*，需手动强转
构造/析构 自动调用构造函数，delete 自动调析构 只搬内存，不碰构造析构
大小 编译器按类型自动算 手动传 sizeof(T)
失败 抛 std::bad_alloc 返回 NULL

必须同族配对：new↔delete、new[]↔delete[]、malloc↔free。混用是未定义行为。

Q：free 释放 new 出来的对象会怎样？反过来 malloc + delete 呢？

A：new + free：对象占的堆内存被还了，但析构函数从未执行——构造函数里申请的子资源（内部 new 的内存、句柄）永久泄漏。malloc + delete 更糟：delete 会对一个从未构造过的对象调用析构，对象成员全是随机垃圾，拿着随机地址去 free——崩溃/堆损坏，未定义行为。一句话：new+free 是"忘了打扫"，malloc+delete 是"对着毛坯房拆装修"。

malloc 三部曲：

  1. 查空闲账本：free 时小块不还 OS，登记进空闲链表（分箱 bins）；申请时按大小查账本，有则拆分返回，顺带合并相邻碎片——全程无系统调用。
  2. 账本没有 → 向 OS 进货：小块走 brk 把堆顶推高，大块（默认 128KB 以上）走 mmap 在映射区开一块，切出所需返回。
  3. OS 也不给 → 才返回 NULL。
Q：为什么 p = realloc(p, newSize) 是危险写法？

A：两个坑。坑一：realloc 失败返回 NULL，直接赋值会让 p 变空，旧块地址丢失——旧数据既用不了也释放不了，泄漏。坑二：成功"搬家扩"时旧块已被释放，其他还存着旧地址的指针全部变野指针。正确姿势：临时指针接收 → 判 NULL → 成功才替换。realloc 的三种结果：原地扩（后面空间够）、新地址（搬家，旧块释放）、NULL（申请失败）。

进程内存布局（低 → 高）：

栈向下、堆向上，相向而长，为彼此腾出空间。栈空间有限（默认约 8MB），但栈帧分配只是挪动栈指针，无系统调用，极快。

⚠️ 易混淆点：野指针 vs 内存泄漏
野指针：指针还在，指向的内存没了（危险，解引用即未定义行为）。内存泄漏：内存还在，指向它的指针没了（不崩，但越用越占内存）。
野指针四大来源：释放后未置空、函数返回局部变量地址、越界、多线程中一个线程释放另一个线程还在用。对应防护：释放即置 nullptr、不返回栈地址、智能指针、线程同步。

④ 智能指针

shared_ptr 结构：对象指针 + 控制块指针（引用计数、弱引用计数、删除器）。多线程同时拷贝/销毁各自的 shared_ptr 是安全的——计数器是原子类型，加 1 减 1 不可分割。

Q："引用计数线程安全，但对象不是"两句话分别是什么意思？

A：第一句：多个线程各自拷贝/销毁自己那份 shared_ptr，计数不会出错，由原子操作保证。第二句：p-> 解引用之后就是普通对象，两个线程同时 p->push_back() 照样数据竞争——shared_ptr 只保证"几个人在用"的计数正确，"几个人同时读写"是否安全一概不负责。

循环引用与 weak_ptr：A、B 互持 shared_ptr 时，双方强计数互相顶住（外部释放后各自剩 1），谁都到不了 0，双双泄漏。weak_ptr 只加弱计数、不动强计数，A 的生死不再依赖 B，死结解开。

规则：强计数归零 → 对象立即析构（与弱计数无关）；弱计数归零 → 控制块才释放（weak_ptr 还要靠它查询状态）。

weak_ptr 不能直接解引用，必须先 lock() 升级成 shared_ptr 再用——升级同时给对象上了”使用期间不死”的保险。

⑤ struct 与 class

C++ 中两者本质是同一个东西，只有两点语法差别：

struct class
默认成员访问 public private
默认继承方式 public private

习惯上 struct 表达纯数据聚合（POD），class 表达有行为、有封装的对象——这是风格约定，不是能力差异。多态、虚函数、模板，两者完全等价。

补充：template 里的 class 与 typename
template <class T> 与 template <typename T> 完全等价，历史遗留的两个关键字。

⑥ delete this

合法，本质是 delete 一个普通指针——对象自己销毁自己，常用于引用计数归零、连接关闭等”无人认领”的时刻。

三条铁律：

  1. 只能用于 new/malloc 出来的堆对象；栈对象 delete this 是未定义行为。常配合私有化构造函数 + 静态工厂方法（create）强制堆分配。
  2. delete this 之后，严禁再访问任何成员、调用任何成员函数——this 已成悬垂指针，函数里剩下的唯一合法语句是 return。
  3. 调用方此后不得再使用该指针。

类比：安乐死——合法执行，但执行后不存在”再去做什么事”，只能结束。

⑦ 内存对齐与缓存行

对齐的本质：CPU 通过内存总线按块取数（64 位机器一块 8 字节），且 L1/L2/L3 缓存与内存之间以缓存行（64 字节）为最小单位搬运——读 1 字节，整条 64 字节一起进缓存。

  • 数据地址是其类型大小的整数倍 → 恰好落在同一块里，一次取全；
  • 错位（跨两块）→ 两次传输再拼接，慢一倍；老架构直接硬件异常。

malloc 一律返回 16 字节对齐的地址：它不知道调用方会存什么类型，按最严标准保证安全。结构体中每个成员按自身对齐要求摆放，不足填充（padding），所以 sizeof 可能大于成员之和——大成员放前面可少浪费尾部填充。

成员地址 = this 的值 + 成员偏移

64 字节对齐与伪共享：两个线程分别写的变量若挤在同一条缓存行里，缓存一致性会让整条行互相失效——两核抢一行，性能暴跌。这就是伪共享。解法是让热点数据独占一行：

例 2 · 配合 SIMD：向量计算要求 16/32/64 字节对齐的加载指令。

⑧ 进程、线程与同步

进程 vs 线程：进程是资源分配的最小单位，线程是 CPU 调度的最小单位。线程共享进程地址空间（堆、全局变量、文件句柄），独享栈和寄存器上下文；线程切换不换页表、不刷 TLB，成本低得多。

同步手段全家桶：

手段 一句话 适用
mutex 独占，同时只允许一个线程 临界区、写操作
信号量 计数器，允许 N 个 连接池限流
读写锁 读共享、写独占 读多写少的面板数据
条件变量 不满足条件就睡，等通知唤醒 生产者消费者（配 mutex）
原子操作/CAS 无锁，硬件保证不可分割 计数器、无锁队列
Q：普通 int 做引用计数为什么线程不安全？

A：count++ 实际执行三步：从内存读到寄存器 → 寄存器加 1 → 写回内存。两个线程穿插执行会读到同一个旧值、各自写回同一个新值——加两次只加了一（丢失更新）。shared_ptr 必须用 std::atomic<int>：硬件把三步锁成一步（x86 上是 lock xadd），别人插不进来。
自旋锁 vs mutex
拿不到锁时：自旋锁原地空转反复检查（while 循环烧 CPU，无系统调用）；mutex 睡过去让出 CPU，等唤醒（睡觉+唤醒开销大，等待期不占 CPU）。临界区极短 + 多核 + 等待时间可预期很短 → 自旋锁；否则默认 mutex。自旋锁的典型实现就是 while (flag.test_and_set()) {}——像陀螺一样原地打转。

lock-free 的概念澄清：它不是”代码里没有锁”，而是一条性质——任何线程停摆，系统整体仍有线程在推进。基于锁的代码里，持锁线程被挂起会拖死所有等待者；CAS 循环没有”谁锁谁”的关系，被挂起的线程只是自己慢点，别人照样成功。更强的 wait-free 保证每个线程有限步内完成（lock-free 只保证”有人能走”，wait-free 保证”人人都能走”）。is_lock_free() 问的是”原子操作在硬件上是否真无锁”，与算法层面是两个问题。代价：CAS 反复失败烧 CPU、ABA 问题、内存序复杂——工程默认用锁，只在剖析证明的热点处上无锁。

线程安全单例（标准答案）：

C++11 起标准保证：函数内 static 局部变量只初始化一次，多线程同时首次调用时只有一个线程执行初始化，其余自动等待，之后零开销——懒加载、线程安全、无 DCL 指令重排坑，一个写法全部解决。老式懒汉双检锁（DCL）需要处理”分配内存 → 构造 → 写指针”被重排成半成品的问题，要靠内存屏障，易写错，已无必要。饿汉式在程序启动（单线程阶段）即创建，天然无线程安全问题，但启动就付账，可能没人用。

⑩ 静态链接与动态链接

静态链接 动态链接
库代码何时进程序 链接时拷进 exe 运行时由 OS 加载 dll/so
exe 体积 大 小
外部依赖 无（自带） 目标机器需有对应库，缺了报”缺少 xxx.dll”
多程序共享 不能，各拷一份 能，内存里一份大家用
库更新 全部重新链接 换库文件即可

类比：静态是出书和引用文字直接抄进自己书里（单看就够，但永远用旧版）；动态是写”详见《XX 手册》第 3 页”（书薄了、手册出新版自动用新版，但读者手里必须有那本手册）。

⑪ static 的四种用法

位置 效果
函数内局部变量 只初始化一次，生命周期延长到程序结束
全局变量/普通函数 限制在本 .cpp 内，其他文件 extern 也链接不到
类成员变量 全类共享一份，不属于任何对象；类内声明类外定义（C++17 可 inline static 一步到位）
类成员函数 没有 this，不能访问非静态成员，可用类名直接调用

文件级 static 是”本文件的私人物品”；类级 static 是”类本身的财产”。

⑫ inline、深拷贝与移动赋值

Q：inline 是性能优化关键字吗？

A：本义是建议编译器就地展开、省掉压栈/跳转开销，但这只是建议——小的简单函数基本总会展开，大的、递归的、虚函数写了也不展开（是否展开由编译器按优化等级自行判断）。它今天真正的主业是让函数定义可以安全写进头文件：普通函数定义写进头文件会被多个 .cpp 包含，链接时报多重定义；inline 函数被特许"多份定义视为同一个"。类内定义的成员函数、模板函数天然带 inline 属性。
注意与 #pragma once 分工不同：pragma once / include guards 管"同一个 .cpp 里头文件别被粘贴两次"（编译期），inline 管"多个 .o 里的机器码算一份"（链接期）。

深拷贝与 Rule of Three/Five：类里有裸指针时，编译器默认生成的拷贝构造是浅拷贝——两个对象的指针指向同一块内存，析构时重复释放，崩溃。深拷贝就是自己写拷贝构造：申请新内存 + 拷内容。

深拷贝/移动赋值/移动构造/析构为什么是一个套餐？

A：需要手写析构 = 类直接管理资源 = 默认拷贝（浅拷贝）必然出错。只写一部分的话，没写的那些编译器会自动生成默认版本，而默认版本全是浅拷贝——只修"释放"环节，"复制"环节还是坏的。所以析构、拷贝构造、拷贝赋值必须一起写（Rule of Three），C++11 起加移动构造、移动赋值（Rule of Five）。现代捷径：用智能指针包装成员，让类不直接碰裸指针，法则自动满足。

移动赋值三步走：① 释放自己原有的资源（否则旧资源泄漏）② 接管对方的资源 ③ 把对方置空（对方析构时不重复释放）。外加自赋值检查 if (this == &other) return *this;——否则 a = std::move(a) 会先删掉自己要接管的资源。移动构造没有"旧资源可放"，所以只有接管、置空两步。

三、易混淆点对比汇总

五、面试金句速记

  1. 指针赋值拷的是地址，值拷贝造的是新对象；新对象的 vptr 由构造它的构造函数决定，与数据从哪拷来无关。
  2. move 只贴标签，搬家靠构造；有名字的右值引用是左值，每层传递资源要自己重新 move。
  3. 普通成员函数是编译器指路，虚函数是对象自己找路——nullptr 没有路标。
  4. 有虚函数的类，析构必 virtual。
  5. new/delete、new[]/delete[]、malloc/free 必须同族配对；混用是未定义行为。
  6. 野指针是”指针在、内存没了”，泄漏是”内存在、指针没了”。
  7. shared_ptr 保证计数正确，不保证对象读写安全。
  8. malloc 三部曲：查账本 → 向 OS 进货 → 才允许失败。
  9. 需要析构函数 = 需要手写全部拷贝家族（Rule of Three/Five），或者用智能指针让法则自动满足。
  10. C++11 之后，线程安全单例 = 一个函数内 static 变量。
  11. inline 的本义是建议展开，主业是解决头文件多重定义。
  12. 临界区短到比”睡觉+唤醒”还便宜才用自旋锁，否则用 mutex。

整理方式：以”提问 → 纠错 → 追问”的复习对话为底稿，按考点编号归档；所有代码均经对话验证。

2.1 综述

洋娃娃工厂例子：流水线各工序并行，产量取决于最慢的工序（bottleneck）。

渲染流程分三个概念阶段：应用阶段、几何阶段、光栅化阶段。划分依据是谁拥有控制权——应用阶段 CPU 控制，后两个阶段 GPU 接管；各阶段之间流水线并行，”应用阶段”在整个帧的时间内持续发生。

Q：图元和片元有什么区别？

A：图元 = GPU 能直接处理的基本几何单位（点/线/三角形，Mesh 和四边形必须拆成这三种）；片元 = 光栅化阶段对被覆盖像素生成的状态集合（插值得到的法线、UV、深度等）。链条：CPU 把 Mesh 拆成图元 → GPU 把图元变片元 → 片元过测试变像素。

2.2 CPU 和 GPU 之间的通信

应用阶段三个任务：准备场景数据（摄像机、视锥体、模型、光源）；粗粒度剔除（culling）；设置渲染状态。输出是渲染图元。

数据流向：硬盘 → 内存（全部渲染数据）→ 显存（GPU 要用的子集）。显卡对显存访问更快、且大多数显卡不能直接访问 RAM；数据进显存后 RAM 副本通常可删，但 CPU 还要做碰撞检测/动画的数据要保留。

Q：内存中的渲染数据 和 GPU 所需的数据相等吗？

A：不相等，是"全集 ⊃ 子集"的关系。第一步是全集（几何、纹理、Shader、材质参数全进 RAM）；第二步是子集——只有 GPU 真正消费的数据进显存：顶点/索引（顶点着色器用）、纹理（片元着色器采样）、参数（MVP、光照等）。碰撞体、骨骼、CPU 剔除用的包围盒留在 RAM。判断标准：这数据接下来被 CPU 用还是被 GPU 用。

渲染状态定义网格怎么被渲染：用哪个顶点着色器/片元着色器、光源属性、材质等。不改状态，所有网格用同一种状态渲染。

Draw Call 就是一个命令，发起方是 CPU，接收方是 GPU，只指向图元列表，材质信息上一步已设好。

2.3.2 顶点着色器

顶点着色器（Vertex Shader）：每顶点调用一次；不能创建/销毁顶点，无法得知顶点间关系，因此可高速并行。两个主要工作：坐标变换和逐顶点光照。

MVP = 模型变换（模型空间→世界空间，即 Transform 组件）、V 观察变换（世界→相机空间，相机变换的逆）、P 投影变换（相机→齐次裁剪空间）。输出仍是四维、w≠1，”压扁”发生在后面的透视除法。

Q：顶点着色器做完 MVP 变换，不就得到最终位置了吗？

A：顶点着色器输出只是齐次裁剪空间坐标，不含屏幕分辨率信息，算不出像素位置。之后链路：裁剪（在齐次裁剪空间，裁剪面 x=±w 等六个平面）→ 透视除法（xyz/w → NDC [-1,1]³，固定硬件自动做）→ 屏幕映射。
Q：顶点着色器里"计算顶点颜色"是干什么用的？顶点着色器都能输出哪些数据？

A："顶点颜色"只是举例——输出统称 varying，"易变"指会被光栅化器插值。顶点着色器可输出颜色、UV、法线、切线等。现代管线颜色多在片元着色器算（纹理×光照），顶点色通道常被挪用：蒙皮权重、动画参数、遮罩。历史原因：固定管线时代属性槽位定死（位置/法线/颜色/UV），颜色槽常空着就借用了；现在可自定义顶点属性（mesh.uv2~uv8），但复用颜色通道零成本、工具链成熟，仍常见。片元颜色 = 顶点属性按重心坐标加权插值的产物。

2.3.3 裁剪

裁剪（Clipping）处理三种关系：完全在内直接传递、完全在外剔除、部分在内则在边界处生成新顶点（位于图元与视野边界的交点）。不可编程，可配置（自定义裁剪平面）。

⚠️ 易混淆点
"裁剪"有两个：CPU 在应用阶段做视锥体剔除（物体级，被剔除的不发 Draw Call）和 GPU 在几何阶段做图元裁剪（部分在内会生成新顶点）。一前一后、一个 CPU 一个 GPU。

2.3.4 屏幕映射

屏幕映射（Screen Mapping）：x、y 从 [-1,1] 缩放到窗口分辨率（如 1080×1920）。z 不处理，与屏幕坐标组成窗口坐标系传给光栅化。

坑：OpenGL 以左下角为 (0,0)，DirectX 以左上角为 (0,0)——图像倒转常因于此。

⚠️ 易混淆点
屏幕映射只负责 NDC → 屏幕像素坐标。"归一化到 [-1,1]³"是独立的透视除法（裁剪后、屏幕映射前，固定硬件自动完成），不在任何可编程阶段。

2.3.5 & 2.3.6 三角形设置与遍历

进入光栅化概念阶段。三角形设置（Triangle Setup）计算光栅化所需信息（边界表示方式）；三角形遍历（Triangle Traversal）判断覆盖哪些像素，并对覆盖区域插值顶点信息（图 2.12 的深度插值例子）。都是固定函数。

重心坐标：插值的权重

定义：三角形 ABC 内一点 P，存在唯一一组 (λ_A, λ_B, λ_C) 满足：
P = λ_A·A + λ_B·B + λ_C·C　　（λ_A + λ_B + λ_C = 1）
几何意义是面积比：λ 的下标是谁，分子就是"把谁换成 P"的子三角形面积：
λ_A = S(BCP) / S(ABC)
即对边与 P 围成的小三角形占整个三角形的比例。P 越靠近某顶点，对应 λ 越大；落在对边上则该 λ = 0。

快速计算：2D 叉积 = 2×2 行列式 = 带符号平行四边形面积。分母 cross(B−A, C−A) 算一次，分子各算一次，第三个用 1 减出来。三个 λ 全非负 ⇔ P 在三角形内——覆盖测试与插值权重是同一组计算；硬件用等价的边函数沿扫描线递推，所以快。

任意属性都走同一公式：
属性|P = λ_A·属性_A + λ_B·属性_B + λ_C·属性_C
法线、UV"凭空出现在片元函数参数里"，就是在这站搭的便车。

2.3.7 片元着色器

片元着色器（Fragment Shader）实现逐片元（Per-Fragment）着色，完全可编程。最重要技术：纹理采样（UV 是插值来的）。DirectX 里叫像素着色器，但”片元”更准确（此时还不是像素）。

片元着色器"知道"什么

输入 = 插值顶点属性 + 自己的屏幕坐标（SV_POSITION），不知道自己在哪个三角形——无三角形 ID、无索引，每次调用互相独立。定位自己靠：屏幕坐标（像素位置效果）；隐式屏幕空间导数（ddx/ddy，GPU 以 2×2 quad 执行可得，mipmap 选级靠它，cross(ddx,ddy) 可重建面法线——书上说的"唯一例外"）。理解"信息孤岛"就通了：为什么做不了"到三角形顶点的距离"、为什么透视校正插值重要。

2.3.8 逐片元操作

逐片元操作（Per-Fragment Operations）：如修改颜色、深度缓冲、进行混合等，不可编程但可配置性很高。流程：片元 → 模板测试 → 深度测试 → 混合 → 颜色缓冲区。

Q：图 2.15 里模板测试、深度测试那一串到底在干什么？

A：模板测试 = 绘画软件里的剪贴蒙版：上层内容只显示在下层有内容的区域，涂出界的部分自动被裁掉。模板测试就是把这套逻辑搬到每个像素上。

机制：每像素一个模板缓冲区（整数 0~255），相当于每格的"蒙版形状"；片元带着参考值来"对蒙版"，条件满足 → 内容显示（继续走深度测试、写颜色）；不满足 → 被裁掉。

经典配合（两次绘制）：第一遍画 A，把 A 的区域"定义为蒙版"（模板=1）；第二遍画 B，按条件被这个蒙版裁剪——B 画不进 A 的区域。

例 1 · 描边：剪贴蒙版的反向用法。先正常画角色 = 定义蒙版（模板=1）；再画放大 3% 的红色角色，条件设为"模板==1 就丢弃"——等于把红色内容从角色轮廓里裁掉，只剩轮廓外多出来的一圈红边。

例 2 · 镜子：标准正向剪贴。先画镜面 = 铺出蒙版形状（模板=1）；再画镜中世界，条件设为"只有模板==1 才许画"——镜像内容被剪贴进镜面的形状里，镜外的部分全部裁掉。

要点：① 模板缓冲全帧共享，用完要恢复状态；② 值是整数，可当计数器（阴影体：正面+1、背面−1，非零即阴影）；③ 只能过滤内容，不能生产内容（内部线靠贴图/rim）。

深度测试 = Z-Buffer 算法：近者胜，胜者写颜色+深度。一句话分工：深度测试管前后遮挡（自动），模板测试管区域通行（程序员布局）。
Q：Blend 就是 α-blend 吗？

A：不是。硬件混合是通用公式：C_final = C_src ⊗ S + C_dst ⊗ D，S/D 可配置。α-blend 只是一种配置：S=SrcAlpha、D=OneMinusSrcAlpha（C_src·α + C_dst·(1−α)）。其他：加法混合（S=D=One，直接相加，火焰/光效，越加越亮）；不混合（直接覆盖）——不透明物体走这个，也是初学者开不出透明的原因。半透明物体必须从后往前画：混合对象是"颜色缓冲区已有的颜色"，顺序错了就混无可混（渲染队列的存在原因）；透明物体通常关深度写入，否则近的玻璃会挡掉后面的东西。

两个补充：

  • Early-Z 技术：测试逻辑上在片元着色器之后，但 GPU 会尽量提前（避免算完颜色才发现被舍弃）。与透明度测试（clip）冲突——着色器可能推翻提前测试的结果，GPU 检测到冲突就禁用提前测试，这就是透明度测试性能下降的原因。
  • 双重缓冲（Double Buffering）：渲染在后置缓冲（Back Buffer），完成后与前置缓冲（Front Buffer）交换，画面连续。

2.4 容易困惑的地方

2.4.1 OpenGL/DirectX 与显卡驱动

OpenGL/DirectX 是图像应用编程接口，架起应用与 GPU 的桥梁：应用发命令 → 接口转给显卡驱动 → 驱动翻译成 GPU 语言 + 把纹理转成 GPU 支持的格式（驱动像”显卡的操作系统”）。

2.4.2 HLSL、GLSL、CG

HLSL（DirectX）、GLSL（OpenGL）、CG（NVIDIA），先编译成与机器无关的中间语言（IL），再由驱动翻译。GLSL 跨平台但编译依赖硬件厂商（结果可能不一致）；HLSL 微软统一编译但几乎仅限微软平台；CG 语法近 HLSL、可无缝移植，但可能用不上 OpenGL 新特性。

2.4.3 Draw Call

误区：以为元凶是 GPU 状态切换。其实”拖后腿”的是 CPU。

为什么 Draw Call 多会卡？——命令缓冲区与批处理

CPU/GPU 靠命令缓冲区（Command Buffer）并行：CPU 添命令、GPU 取命令。每次 Draw Call 前 CPU 要做大量准备（检查渲染状态、打包数据），GPU 渲染极快（200 和 2000 个三角网格区别不大），提交速度跟不上渲染速度——Draw Call 太多，CPU 卡在提交里，GPU 空闲。类比：复制 1 万个 1KB 小文件远比复制一个 10MB 文件慢，开销在"动作"不在数据量。对策是批处理（Batching）：CPU 内存中合并小网格一次画完。注意：① 合并耗 CPU，适合静态物体（动态物体每帧重合并反而亏）；② 避免大量小网格、避免过多材质（材质不同合不了批）。

2.4.4 固定管线渲染

早期 GPU 只能配置不能编程；如今固定管线已退出历史舞台（OpenGL 3.2 Core Profile 完全移除），维护老项目才需要学。

2.5 什么是 Shader

一句话：Shader 就是 GPU 流水线上一些可高度编程的阶段（顶点/片元着色器必写，细分/几何着色器可选）。出色画面需所有阶段配合：渲染状态、混合函数、深度测试/写入的开关。

易混淆点对比汇总

易混淆对 一句话辨析
图元 vs 片元 图元 = GPU 直接处理的几何单位（点/线/三角形）；片元 = 光栅化后覆盖像素的状态集合
CPU 视锥剔除 vs GPU 裁剪 前者应用阶段、物体级、不发 Draw Call；后者几何阶段、图元级、会生成新顶点
可编程 vs 可配置 可编程 = 写 Shader 代码；可配置 = 只能填参数（模板/深度/混合都是后者）
深度测试 vs 模板测试 深度管前后遮挡（近者胜，自动）；模板管区域通行（挡板，程序员布局）
投影变换 vs 透视除法 投影矩阵只把深度编进 w；压扁成 NDC 的是之后的透视除法
屏幕映射的范围 只负责 NDC → 屏幕像素坐标；透视除法到 NDC 是独立一步
Blend vs α-blend Blend 是通用混合公式；α-blend 只是一种因子配置（还有加法混合、不混合）
模板测试 vs 深度学习 mask 同一思想：逐元素挡板、入口过滤
Gouraud vs Phong 着色 逐顶点光照+插值 vs 插值法线后逐片元光照（主流，避免大三角面明暗跳变）

Godot 4 P2P 联机基础 —— ENetMultiplayerPeer 与 RPC 注解

📇 速览卡片（3 分钟复习）

概念 一句话
ENet 基于 UDP 的可靠传输库，Godot 4 内置封装
ENetMultiplayerPeer 端对端（P2P）联机的核心实例，替代底层 Socket 管理
call_remote RPC 只发远端，本地不执行
call_local RPC 本地与远端同时执行
authority 仅该节点的网络权限所有者（通常是房主/服务器）可调用
any_peer 任意对等体均可调用
reliable 保证送达，适合状态变更、扣血
unreliable 不保证送达，适合高频位置同步
unreliable_ordered 不保证送达，但保证顺序，适合连续动画帧
通道 (Channel) 0~9 共 10 条，类似端口分流，可分别设带宽上限

📝 详细笔记

1. Host 与 ENetMultiplayerPeer

Godot 4 的 P2P 联机基于 ENet 库，底层走 UDP 协议。开发者不需要手动处理 Socket、NAT Punch-through 或数据包序列化，直接通过 ENetMultiplayerPeer 一个高层实例完成端对端管理。

ENetMultiplayerPeer.new() 即为一个完整的端对端实例，封装了连接管理、心跳、丢包重传等细节。

2. @rpc 注解四参数

Godot 4 使用 @rpc(...) 标记远程调用函数，四个位置参数决定了网络行为的全部策略：

A —— 执行范围（本地 vs 远端）

取值 语义
call_remote 仅远端执行，本地不执行。适合”通知别人”
call_local 本地 + 远端全部执行。适合确定性逻辑，确保所有端状态一致

B —— 调用权限（谁能发起）

取值 语义
authority 仅该节点的网络权限所有者（默认是创建它的端，通常是 Host）可以调用。防作弊首选
any_peer 任意对等体均可调用。适合玩家输入、自由交互

C —— 传输可靠性

取值 语义 适用场景
reliable 保证送达，丢包会重传，可能延迟 状态变更、扣血、拾取道具、游戏开始/结束
unreliable 不保证送达，不重传，最低延迟 高频位置同步、旋转、速度
unreliable_ordered 不保证送达，但保证顺序 连续动画帧、弹道轨迹，允许丢帧但不允许乱序

D —— 通道编号 (Channel)

  • 取值范围：0 ~ 9，共 10 条独立通道
  • 作用类似端口分流：不同通道的数据互不阻塞，可分别设置带宽上限
  • 典型用法：
    • 通道 0：reliable 状态同步（低带宽、高优先级）
    • 通道 1：unreliable 位置同步（高频、可丢包）
    • 通道 2：聊天/语音（独立带宽限制）
